# 아키텍처: 하나의 senpi 세션, 독립 도메인 도구, Azure 모델

## 결정

**운영자가 쓰는 작은 앱 + senpi SDK 세션 1개 + 재사용 가능한 도메인 도구 + Azure OpenAI Responses**를 권한다. 같은 도구를 공식 extension으로도 등록하여 개발자가 CLI에서 점검한다. “플러그인만 만드는 제품”도 “Foundry 에이전트와 senpi가 서로 계획하는 이중 에이전트”도 기본안이 아니다.

이는 설계 결정이다. 현재 저장소는 타입·extension 등록·상태 조회 골격뿐이고 웹 앱, 도메인 판단, Azure 호출, MCP 서버는 구현하지 않았다.

## 대안 비교

판단 기준은 네 명, 11/25 발표, 폐플라스틱 우선, 실제 구현은 팀원이라는 제약이다. 아래 1–5는 **설계 선택용 주관적 유리함**이며 실제 심사 점수/실측 성능이 아니다. 높을수록 유리하고, 난이도 열은 쉬울수록 높다.

| 대안 | 심사 증거 확보 | 구현 용이 | 데모 안정 | Azure 노출 | 유지보수 | 합계 /25 | 판단 |
|---|---:|---:|---:|---:|---:|---:|---|
| CLI extension만 | 3 | 5 | 4 | 3 | 4 | 19 | 개발 속도 유리, 현장 사용자 UX와 전달력 약함 |
| skill만 | 2 | 5 | 2 | 2 | 3 | 14 | 지침은 쉽지만 규칙/계산/근거 강제 불가 |
| 도구 패키지 | 3 | 4 | 4 | 3 | 5 | 19 | 배포 경계에 유리, 자체 사용자 앱이 아님 |
| MCP 서버 + senpi | 4 | 3 | 3 | 3 | 4 | 17 | 다중 클라이언트 수요가 있을 때, 지금은 transport 비용 |
| **SDK 앱 + 얇은 extension** | **5** | **3** | **4** | **4** | **4** | **20** | **권장: 사용자 보고서와 실행 재현을 함께 확보** |
| Foundry 네이티브 agent + senpi | 4 | 2 | 2 | 5 | 2 | 15 | Azure 관리 화면 강점, 이중 상태/인증/배포 부담 |

점수는 선택 이유를 드러내는 보조 도구다. SDK 앱 구현 경험이 없거나 11/10 E2E 연결 실패 시 CLI extension을 **발표용 단기 대안**으로 줄일 수 있으나 현장 사용성 한계를 밝혀야 한다. 운영진이 Foundry Agent Service 사용을 별도 의무화하면 ADR을 갱신하고 단일 운영 오케스트레이터를 다시 선택한다.

### 공식 20점 항목별 구조의 영향

- 문제해결력 20: 어떤 host든 실패·개선 실험이 핵심. SDK는 실행 로그를 사례와 연결하기 쉽다.
- 현장 적용성 20: 앱 입력/보고서가 터미널보다 담당자에게 적합하다. 팀 역량은 검증 필요.
- 창의성 20: MCP/멀티에이전트 자체가 아니라 부족한 사실을 물어 대안을 바꾸는 판단이 증거다.
- 전달력 20: 한 사례·한 실행·한 보고서. 이중 agent loop는 설명 비용을 키운다.
- 판단 신뢰성 20: skill만으로는 부족하다. 모든 방식에서 결정적 규칙·계산·출처 검증이 필요하다.

## 실제 API 근거

2026-11-05 registry 확인: `@code-yeongyu/senpi@2026.11.4-2`, Node `>=24`. MIT 선언. `docs/senpi-and-azure.md`의 버전별 파일/행에 근거를 적었다.

공식 확장점은 default `ExtensionFactory(pi: ExtensionAPI)`와 `pi.registerTool(defineTool(...))`이다. 배포 패키지 메타데이터는 `pi.extensions`, `pi.skills` 키다. `createPlugin` 같은 추정 API는 쓰지 않는다. SDK는 `createAgentSession`, `DefaultResourceLoader`, `ModelRuntime`, `SessionManager`를 export한다.

MCP는 senpi가 지원하는 별도 client/server 경계다. 도구를 등록했다고 MCP 서버가 되는 것은 아니다. Foundry 관리형 Agent Service와 Azure OpenAI 모델 호출도 다르다.

## 처리 흐름

```text
사진 + 설명 + 공정/성상/지역/물량/기준일
  -> 경계 입력 파서 및 누락 질문
  -> 케이스별 senpi SDK session (Azure OpenAI Responses)
       -> 재질/분류 후보 제안 (확정 아님)
       -> 버전 고정 근거 조회
       -> 재사용/재활용/기타 회수/처분의 조건별 적합성
       -> 검증된 지역 업체 snapshot 필터
       -> 동일 조건 비용·탄소 계산
  -> host의 결과 검증 및 보류 게이트
  -> 사람이 읽는 조건부 비교 보고서 + 근거/실행 기록
```

도메인 코어는 senpi·Azure·MCP·UI를 import하지 않는다. `src/contracts.ts`는 팀 합의를 위한 입력·출처·판정·비교 계약이며 런타임 유효성 검증 구현이 아니다. 공통 타입은 팀장 리뷰 후 변경한다.

| 경계 | 입력 → 출력 | 구현 책임 |
|---|---|---|
| 입력 | 사용자 원문 → CaseInput 또는 오류 | 단위/날짜/크기/이미지 타입 파싱, 질량 0·음수 처리 |
| 식별 | 사진+공정 → 수지/코드 후보+필요 질문 | 외관에서 알 수 없는 유해성/수지 혼합 추정 금지 |
| 근거 | case+평가일 → EvidenceRecord 목록 | 적용 대상·시행일·locator·hash·라이선스 유지 |
| 판정 | case+근거 → RouteAssessment | eligible/ineligible/unknown 분리 |
| 업체 | route+case → ProcessorCandidate | 허가 코드·지역·조회일, 인수 의사 별도 |
| 계산 | 동일 질량/경계+근거 계수 → ScenarioComparison | 숫자는 일반 코드가 계산, 모델 숫자를 권위로 쓰지 않음 |
| 보고서 | 검증 결과 → DecisionResult | 검증된 내용만 렌더링, 인간 승인 상태 유지 |

### 계산 계약

`ComparisonInput`은 CaseInput과 별도로 caseId에 연결한다. `baselineRouteId=null`은 기준선 미확보이며 소각을 기본값으로 넣지 않는다. 경로별 `QuoteInput`은 quoteId, 단위가 맞는 요율/물량, VAT, 유효기간, 포함된 다른 견적, 매각수입 귀속을 보존한다. 같은 case에 견적 A/B를 따로 연결할 수 있다.

`ActivityInput`은 활동량·단위·단계와 factorId/version을 전달한다. `ComparisonInput.factors`와 factorRegistryVersion은 계산 시점에 고정된 계수 묶음이고 모든 숫자는 EvidenceRecord로 연결한다. registry에 없는 ID, 단위 불일치, 권리 미검증, 누락 값, 범위 중복은 계산 담당의 경계 파서에서 거부/보류한다. 대체 크레딧도 승인된 활동량·계수 없이는 unavailable이다.

`ScenarioComparison`은 비용 항목과 quoteId, 탄소 항목과 activity/factor 버전, 순비용, 총배출, 원료/에너지 크레딧, 순배출, 기준선 대비 회피량을 분리한다. 기준선이 없으면 회피량은 `no-baseline`이다. 총배출을 계산할 자료가 있어도 감축량이 자동으로 생기지 않는다. 보고서는 자유 서술을 다시 계산하지 않고 이 구조를 읽는다.

`src/comparison.examples.ts`는 같은 case의 두 견적 연결과 기준선 없는 출력을 타입체크하는 **숫자 없는 형식 예시**다. 실제 견적·계수나 계산기 구현이 아니다.

## 신뢰성 규칙

1. 사진만으로 법적 코드·유해성·적법성을 확정하지 않는다. 발생 공정/원료/SDS 등 추가정보가 필요할 수 있다.
2. 출처가 말하지 않는 것을 “아니다”로 바꾸지 않는다. 누락·모순·오래된 자료는 unknown/needs-review.
3. 인용 URL뿐 아니라 문서의 조항/표/페이지/데이터 행과 해당 판단을 연결한다. RAG 검색 성공은 인용 일치의 증거가 아니다.
4. 신뢰도는 근거 충족/누락/모순, 판단별 검토 상태로 표시한다. 검증되지 않은 92% 확률을 만들지 않는다.
5. 업체 목록 등재는 처리 허가와 인수 의사의 증명이 아니다. 허가 코드/처리 범위, 날짜, 실제 확인을 구분한다.
6. 비용·탄소가 없으면 unavailable. 0이나 모델 상식으로 대체하지 않는다.
7. 최적은 모든 경우에 단일 1등이 아니다. 법적/기술적 적합성 먼저, 그 안에서 비용·탄소 Pareto 후보와 사용자의 우선순위를 제시한다. 범위가 겹치면 순위를 보류한다.
8. 보고서는 의사결정 지원이다. 현장 담당자 확인 전 실제 반출/계약/처리 실행을 자동화하지 않는다.

## 운영 경계

### 서버의 후보 순위 규칙 (2026-11-12)

`src/ranking.ts`는 모델 응답이나 선호 가중치 없이 검증된 비교 결과에서 순위군을 계산한다. 공통 `DecisionResult` 계약은 바꾸지 않고 서버 보고서 렌더링 시 계산하여 화면과 인쇄 보고서에 같은 결과를 표시한다.

- 대상은 `eligible` 경로의 대안이다. 같은 경로의 견적 A/B도 독립 대안으로 다룬다. 부적합·미확인은 순위 보류다.
- 사업자 순비용(KRW)과 순배출(kgCO2e)을 모두 작을수록 좋다고 본다. 음의 순배출을 탄소 제거로 해석하지 않는다. 기능단위 또는 계산 경계가 다르면 순위를 보류한다.
- A의 비용 상한이 B의 비용 하한 이하이고 A의 순배출 상한이 B의 순배출 하한 이하이며, 하나 이상 엄격히 작을 때만 A가 B보다 우월하다. 중앙값만으로 범위의 중첩을 무시하지 않는다.
- 다른 후보에 지배되지 않는 후보가 1순위군이다. 이들을 제거한 다음 같은 규칙으로 2순위군 이후를 구한다. 같은 군의 정확한 동률·비용/탄소 상충·범위 중첩은 군 내 순위 보류다. 군 내 입력 순서는 표시 순서일 뿐이다. 비용과 탄소를 환산하거나 임의 가중합으로 단일 1등을 만들지 않는다.
- 순비용 또는 순배출이 `unavailable`인 대안은 결측값을 0으로 대체하지 않고 순위 보류와 계산 불가 이유를 함께 표시한다. 비교 가능한 후보가 2개 미만이면 순위를 매기지 않는다. 순위군은 계산 가능한 후보 사이의 상대 순위이며 미확인 후보보다 우월하다는 뜻이 아니다.
- 보고서는 대안 이름·순위군·순비용·순배출과 우월한 입력 대안 번호를 표시한다. 기존 질문/검토 보류 상태와 인간 승인 대기는 바꾸지 않는다.

- 케이스별 독립 세션, 동시 요청 사이 상태 공유 금지. 사용자 세션/인증 구현은 팀 작업이며 현재 골격에는 없다.
- 사용자 앱에 bash/read/write 등 일반 코딩 도구를 노출하지 않는다. `tools` 허용 목록과 host 권한 검사를 적용한다.
- `noExtensions`가 내장 extension까지 없애지는 않는다. 앱 전용 `agentDir`, OS 최소권한, 네트워크/파일 권한 제한이 필요하다. 이 설계 자체가 sandbox 구현을 의미하지 않는다.
- 사진 EXIF·사업장 개인정보·법적 민감 정보를 최소화하고 입력 동의/보관 기간을 정한다. 개발 원본은 개인 공간, 레포에는 허가된 비식별 예시만 둔다.
- 소스/모델 호출의 timeout·취소·오류를 단계 상태로 보존한다. 인증 실패를 모델 답변으로 감추지 않는다.
- 11/20까지 고정한 source snapshot을 데모에 사용할 수 있으나 “실시간 조회”라고 표시하지 않는다. 서비스 장애 시 사전 녹화로 전환하고 그 사실을 표시한다.
