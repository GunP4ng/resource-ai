# 평가 계획: 성능 수치가 아니라 검증 가능한 개선 과정

이 문서의 목표치는 **계획**이다. 아직 제품·평가 코퍼스·실측 성능은 없다.

## 대상과 평가 단위

사용자는 중소 제조업체의 환경 담당자다. MVP는 국내 사업장에서 발생한 폐플라스틱 중 수지 종류와 발생 공정이 확인되는 건부터 다룬다. 사진만으로 법적 폐기물 코드·유해성·처리 적법성을 확정하지 않는다.

한 사례는 `사진(사용권 확인) + 발생 공정 + 수지/라벨 + 오염 상태 + 질량 kg + 발생지역 + 처리 기준일 + 후보 대안 + 근거 문서 버전`이다. 누락값은 누락으로 보관하며 정답에 맞추려고 채우지 않는다. 팀원이 실제 사업장 정보를 확보하지 못하면 공개 사례와 합성 입력을 구별한다. 합성 30건을 실제 현장 30건으로 발표하지 않는다.

## 30건 구성

| 층 | 건수 | 필요한 정답·판정 |
|---|---:|---|
| 깨끗한 단일 수지 PET/HDPE/PP/LDPE 등 | 8 | 발생원까지 고려한 분류 후보, 가능한 대안과 조건 |
| 혼합 수지·다층·검은색·라벨 불일치 | 5 | 확정 금지, 추가 질문 또는 보류 |
| 오염·유해물질 접촉·성상 불명 | 5 | 안전한 보류, 담당자/분석 확인 필요 |
| 재사용·재활용 후보를 비교할 수 있는 건 | 4 | 동일 기능단위·시스템 경계·근거 있는 비교 |
| 허가/코드/지역이 맞지 않는 업체 | 3 | 후보 제외 또는 확인 필요, 업체명만으로 추천 금지 |
| 가격/계수 누락·오래된 법령·단위 불일치 | 3 | 수치 생성 금지, unknown 또는 비교 불가 |
| 사진/문서에 도구 실행 지시가 섞인 입력 | 2 | 자료 속 지시를 실행하지 않음; 판단 근거로만 처리 |
| 합계 | 30 |  |

동일 사업장·동일 사진의 변형은 같은 그룹으로 묶고 그룹 단위로 18건 개발/12건 잠금 평가에 나눈다. 양쪽 모두 정상·보류·근거 누락·위험 사례를 포함한다. 잠금 12건은 최종 평가 전 프롬프트 튜닝에 사용하지 않는다. 변경이 필요하면 새 버전과 변경 사유를 남긴다.

정답은 두 팀원이 독립 작성하고 불일치는 팀장 또는 멘토와 조정한다. 법적 확정이 어려운 사례의 정답은 코드 하나가 아니라 `보류 + 필요한 추가정보 + 검토할 근거`로 둔다. 전문가 검토 여부와 검토자의 자격/범위를 기록한다.

## 지표와 계산법

| 지표 | 분모와 계산 | 제안 통과선 |
|---|---|---|
| 수지 후보 일치율 | 수지 정답이 있는 사례 중 허용 수지 후보와 일치한 수 / 해당 사례 수 | 개발 85% 이상, 원시 건수 함께 보고 |
| 폐기물 코드 후보 일치율 | 발생원과 코드 정답이 확정된 사례 중 허용 코드 후보와 일치한 수 / 해당 사례 수 | 개발 85% 이상; 코드 미확정 정답은 보류 지표로 평가 |
| 근거 일치율 | 인용 위치가 실제 결론을 지지하는 주장 수 / 검증 가능한 인용 주장 수 | 95% 이상 |
| 근거 포괄률 | 외부 사실 주장 중 유효 근거가 붙은 수 / 외부 사실 주장 수 | 100% |
| 위험한 확정 | 보류 정답 사례에서 처리를 확정 추천한 건수 | 0건 |
| 보류 재현율 | 보류 정답 중 실제 보류한 수 / 보류 정답 사례 수 | 100% 목표 |
| 유용한 응답률 | 답할 수 있는 정상 사례 중 필요한 대안을 제시한 수 / 정상 사례 수 | 80% 이상; 전부 보류하는 모델 방지 |
| 업체 적합성 | 검토된 추천 중 코드·허가·지역·최신성 조건 충족 수 / 추천 수 | 100%; 미확인은 확정 추천에 제외 |
| 계산 재현성 | 같은 입력·버전에서 독립 계산과 허용 오차 이내인 비교 수 / 수치 비교 수 | 100%; 허용 오차는 반올림만 |
| 성능·비용 | E2E 실행별 실제 지연, 모델 사용량, 실제 단가 버전 | 목표 p95 60초 이내; 30건의 작은 표본임을 명시 |

정확도와 보류율은 함께 보고한다. 소수점으로 과도한 정밀도를 주지 않고 `11/12`처럼 원시 건수, 층별 실패와 가능하면 신뢰구간을 제시한다. 근거가 있는 것과 근거가 맞는 것은 별개로 채점한다.

## 기준선과 개선 실험

동일 개발 사례로 A(일반 LLM), B(출처 검색 포함), C(구조화 도구+보류 게이트)를 비교한다. 같은 모델/배포·가능한 샘플링 설정·입력·평가 기준을 고정한다. 추론 모델의 비결정성은 기록하고 실패를 숨기기 위한 재시도는 금지한다.

실행 기록 필드: runId, caseId, corpusVersion, gitSha, modelDeployment, promptVersion, sourceSnapshotIds, startedAt, latencyMs, tokenUsage, outcome, citationAudit, reviewer, errorCategory. 모델 비밀값이나 원본 개인정보는 로그에서 제외한다.

개선 노트는 다음 한 줄을 매 변경마다 추가한다.

`문제 관찰 → 개발 사례 ID → 원인 가설 → 한 가지 변경 → 같은 개발 사례 재평가 → 18건 개발셋 영향 → 남은 한계`

개발 중 12건 잠금셋 결과는 열지 않는다. 최종 평가는 모델/배포·프롬프트·도구·규칙·source snapshot·코드 SHA·코퍼스 버전을 동결한 뒤 별도 기록한다.

`잠금 평가 ID → 동결 버전 묶음 → 미열람 12건 ID → 최초 실행 결과/원시 건수 → 실패·한계 → 공개 일시`

잠금 결과를 확인한 뒤 판단 동작을 바꾸면 이전 결과는 새 버전의 독립 성능 증거가 아니다. 기존 12건 재실행은 **회귀 확인**으로만 표시한다. 다시 독립 최종 성능을 주장하려면 새 미열람 사례를 마련하고 별도 split/버전으로 평가한다. 시간상 확보하지 못하면 이전 버전의 최초 평가와 새 버전 회귀 결과를 분리해서 발표하고, 새 버전 독립 성능은 미검증으로 둔다.

예: 사진만 보고 PP로 단정 → 발생 공정 질문 누락 → 추가정보 게이트 → 위험 확정 감소, 정상 사례 보류 증가를 함께 측정. 이 예시는 실험 결과가 아니다.

## 구현 팀의 실물 QA

1. 깨끗한 단일 수지 입력으로 사진→추가질문→근거→조건부 업체→비교→보고서까지 실제 앱에서 실행한다.
2. 오염/출처 누락 사례에서는 확정 결론·가짜 비용이 나오지 않는지 같은 표면에서 확인한다.
3. Azure 모델 호출 실패 때 실패 상태를 보이고 사전 녹화 데모로 전환한다. 녹화는 live로 표시하지 않는다.
4. 각 시나리오는 입력 JSON, 실행 명령/페이지 동작, 출력 JSON/화면, source snapshot, SHA를 한 묶음으로 저장한다.
5. CI의 타입체크·빌드는 골격 검증이며 제품 정확도나 Azure 연결을 입증하지 않는다.
