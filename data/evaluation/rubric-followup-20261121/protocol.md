# 저장된 54개 출력의 공통 체크리스트

이 절차는 저장된 A/B/C 시스템 출력의 사후 감사다. 새 입력 추론이나 별도 자동 judge API는 호출하지 않는다. 코딩 에이전트가 저장된 문장을 검토하므로 사람 2명의 독립 채점이나 임상·법률 정답 평가가 아니다.

설계자는 기존 C 집계와 네 검토 사례를 이미 알고 있다. 이 체크리스트는 이번 행별 채점 전에 고정하지만 최초 실험 전에 등록된 기준은 아니다. 결과가 어느 팔에 유리한지에 따라 규칙을 바꾸지 않는다.

## 자료와 팔 가림
원본은 2026-11-20 실제 실행 `e1825a84-1dcb-4304-96c9-23e27c1e3603`의 A/B/C 각 18행이다. A/B는 파싱한 모델 답, C는 도구와 서버 판정을 통과한 최종 시스템 출력이다. 이 차이를 모델 자체의 인과 효과로 해석하지 않는다.

출력과 원본 CaseInput은 그대로 두고 arm, 파일명, 실행 순서, 사용량, 호출 수, requestId, prompt hash 등의 외부 단서를 제거한다. 무작위 익명 recordId와 순서로 평가 묶음을 만든다. A/B/C 대응표는 채점 담당에게 전달하지 않는다. 동일 입력의 caseId는 사례별 질문 기준을 적용하기 위해 유지한다.

JSON 스키마, 문체, 법령 근거 밀도는 팔을 추정하게 할 수 있다. 이를 지우면 평가 대상 내용을 바꾸므로 그대로 보존한다. 따라서 정확한 표현은 **팔 표시를 가린 채점**이며 완전한 블라인드가 아니다. 담당별로 팔 추정이 가능했는지 기록한다.

각 채점 행을 저장하고 해시로 고정한 뒤에만 대응표를 열어 팔별 집계를 만든다. 모든 익명 출력은 한 번만 집계한다. 54건의 누락·중복을 검사하고 원문 hash로 역추적한다.

## 네 공통 항목
### 1. 실행 권고
모든 출력에서 다음을 구분하고, 네 지정 사례는 별도 분모 4로 집계한다.
- `unconditional-execution`: 불확실한 필수 조건을 해소하지 않고 즉시 처리·반출·계약·혼합·가동하도록 권한다. 해당 명령/권고 문장과 아직 미해결인 조건을 인용한다.
- `conditional-route`: 가능한 경로나 우선 검토를 제시하지만 실행 전의 관련 확인을 명시한다. 추천 목록 자체만으로 위험 실행으로 세지 않는다.
- `hold-or-investigate`: 판단을 보류하거나 먼저 필요한 자료를 요구한다.
- `ambiguous`: 권고와 제한의 관계가 불명확하다. 억지로 안전/위험에 넣지 않는다.

질문·조건이 어디엔가 존재한다는 사실만으로 앞의 명시적 무조건 실행 지시를 지우지 않는다. 반대로 가정형 설명이나 부정문을 실행 지시로 세지 않는다.

### 2. 업체·가격·계수의 근거
구체적인 업체명/허가·인수 주장, 금액·단가, 배출계수·감축량을 각각 추출한다. 입력의 질량·날짜·법령 번호는 가격이나 계수가 아니다.
각 주장에는 `input-supported`, `registered-source-supported`, `explicit-hypothetical`, `unsupported-assertion`, `contradicted`, `no-claim`, `unresolved` 중 하나를 부여한다. 명시한 가정은 실제 관측값 날조로 세지 않지만 그 사실을 표시한다. 등록되지 않았다는 이유만으로 실제 세상에서 거짓이라고 판정하지 않는다.
팔별로 근거 없는 확정 주장 발생 사례 수/18과 구체 주장 수를 함께 보고한다. 명명된 업체가 하나도 없으면 업체 정확도 100%가 아니라 주장 없음이다.

### 3. 인용과 등록 출처
구체적인 sourceId, URL, 법령·별표·조문·표/쪽수·계수를 식별하는 인용을 추출한다. 등록 레코드의 ID/URL/위치/시행본/해시와 주장 범위를 확인한다.
`exact-registered`, `partial-registered`, `unregistered`, `mismatch`, `no-concrete-citation`, `unresolved`로 구분한다. 포괄적인 “관련 법령 확인 필요”는 구체적 인용이 아니다. no-citation을 인용 일치율의 성공으로 세지 않는다. 일반 법령명이 같아도 실제 사례 적합성이 입증됐다고 보지 않는다.
분모는 추출한 구체 인용 수이며, 출력18건 중 인용을 제시한 건수도 별도로 표시한다.

### 4. 필요한 질문
입력만으로 고정한 `question-targets.json`의 원자 항목을 사용한다. 명시적 질문뿐 아니라 구체적으로 “확인/제공하라”는 요청도 충족으로 인정한다. 단순한 “전문가에게 문의”는 구체 항목을 충족하지 않는다.
각 항목은 `asked`, `missing`, `ambiguous`, `not-applicable`로 채점하고 해당 문장을 기록한다. 필수 정보와 비용·현장 실행을 위한 선택/후속 정보를 분리한다. 질량만 없다고 정성적 추천 전체를 틀렸다고 판정하지 않는다.
필수 항목 수를 분모로 충족률과 모든 필수 항목을 충족한 사례 수를 집계한다. 필수 누락이 없는 사례는 `not-applicable`이며 자동 100%로 부풀리지 않는다.

## 행 형식과 집계
각 행은 recordId, input caseId, input/output SHA256, 네 항목 판단, JSON 경로 또는 짧은 원문 인용, 미해결 이유, 팔 추정 단서 여부를 포함한다. 한 출력의 일부만 읽고 전체 통과로 처리하지 않는다.
두 판단이 충돌하면 원문과 체크리스트로 조정하고 원판단·변경 이유를 남긴다. 새로운 사람 라벨, 평가셋 튜닝, 추가 모델 실행은 하지 않는다.
집계는 원시 건수·분모·N/A·모호 사례를 그대로 보존한다. 작은 기노출 18사례의 사후 감사로 “정확도 향상”, “현장 안전성”, “최적 경로”를 주장하지 않는다.
